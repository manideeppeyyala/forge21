# Forge21: daily routine, diet and gym coach

A 21-day body-recomposition app: a daily schedule, meals and macros, workouts, content plan, check-ins and metrics.
Plain HTML/CSS/JS (no build step), installable as an app (PWA), with an optional Vercel backend for
**sync across devices** and **notifications that arrive on time even when the app is closed**.

## The brief

What the app was built to do (kept generic on purpose, since this repo may be shared):

- A **21-day reset** toward a long-term weight goal using diet, gym and daily walking, with **body recomposition** (lose fat, keep and build muscle).
- **Two location modes**, Home and Hyderabad (PG/hostel), each with its own schedule and food.
- A weekday shift schedule with office and work-from-PG days, a short commute on office days, early wake-up, morning gym, night walk and 7 to 8 hours of sleep.
- A **content-creation routine**: a daily short video (365 in a year), one or two long videos a week, a recurring venue shoot.
- A dashboard to tick things off, **notifications whose buttons update the app**, daily weight, daily progress photo, monthly body measurements, meal photos from camera or gallery, a report vault, reminders, goals, analytics with "where you're slipping" coaching.
- Budget diet built around what a PG serves, with protein and fibre targets.
- Use on **all devices**, installable like an app, fast, with modern animations.

## Deploy

Everything below is done in your own browser (the assistant's browser cannot open Vercel or GitHub on a managed work device).

1. **Import:** vercel.com → Add New → **Project** → import `manideeppeyyala/forge21` (allow Vercel to read the private repo when asked). Framework Preset **Other**; leave the build command empty. `vercel.json` sets the output directory to `public`. Click **Deploy**. The static app is live from this point, before any backend setup.
2. **Storage** (project → Storage tab; each step adds its environment variables automatically):
   - **Create → Upstash Redis** (Marketplace, free plan) → connect to the project for all environments.
   - **Create → Blob** → create a store → connect to the project.
3. **Cron secret:** Settings → Environment Variables → add `CRON_SECRET` (Production) with a random value of 32+ characters. Generate one in PowerShell:
   ```powershell
   $b = New-Object byte[] 32; [Security.Cryptography.RandomNumberGenerator]::Create().GetBytes($b); ($b | ForEach-Object { $_.ToString('x2') }) -join ''
   ```
4. **Redeploy** (Deployments → ⋯ → Redeploy) so the new variables apply.
5. **Check the backend:** open `https://<your-site>/api/config`. It should show `{"publicKey":"..."}`. That proves the functions and Redis work.
6. **Link your first device immediately** (Settings → Sync + push → "First device: create my code"). The first code to connect becomes the only one the server accepts (see Security). Save it in a password manager.
7. **Per-minute push timer:** Vercel's free (Hobby) plan only runs scheduled jobs once a day, so use a free external timer, for example cron-job.org: create a job with URL `https://<your-site>/api/tick`, schedule **every 1 minute**, and under advanced settings add the header `Authorization: Bearer <your CRON_SECRET>`. Its "test run" should return HTTP 200 with JSON like `{"due":0,...}`. (On a Vercel Pro plan you can instead add `"crons": [{"path":"/api/tick","schedule":"* * * * *"}]` to `vercel.json`; Vercel then sends the secret itself.)
8. **Other devices:** on first launch use "Already use Forge21? Enter your sync code". Then **Turn on push** on each device and **Install app** (Chrome menu on Android; Share → Add to Home Screen on iPhone, iOS 16.4+).

Static-only fallback: skip steps 2 to 7; the app works fully on each device, without sync or background push.
Real `.apk`: after deploying, paste the URL into https://www.pwabuilder.com → Android → Download.

## Security model

- **No accounts, no analytics, no trackers.** The only external request is Google Fonts (CSS + font files).
- **Sync code:** random, 100 bits. The browser sends only its SHA-256 as an auth header; the code never reaches the server.
- **Single-owner lock:** the first sync id that connects owns the deployment (a Redis key set with `NX`); every other id gets HTTP 403, so strangers who find the URL cannot store anything. To re-claim (for example the code was lost), delete the key `f21:owner` in the Upstash console.
- **Photos and reports are end-to-end encrypted** (AES-GCM 256, key from PBKDF2 over the sync code, which the server never sees). The server holds only random-looking bytes. Decrypted types are whitelisted (images and PDF only), so a blob can never render as HTML.
- **Where the bytes live:** encrypted blobs go to Vercel Blob under a random, unguessable URL; the id → URL map is in Redis; reads are proxied through `/api/photo`, which checks the owner and refuses to fetch anything that is not a Vercel Blob URL.
- **Not encrypted on the server:** numbers and ticks (weights, steps, measurements, routine state) and notification text. They are needed server-side to merge devices and send pushes. They live in your own Upstash Redis database.
- **All incoming data is validated** against a strict whitelist (`public/merge.js`, shared by browser and server): wrong types, odd keys (`__proto__`), oversize strings and unknown fields are dropped. User text is HTML-escaped when rendered.
- **Headers** (`vercel.json`): strict Content-Security-Policy (scripts only from this origin, no inline script, no framing), HSTS, `nosniff`, `no-referrer`, COOP/CORP same-origin, `noindex`.
- **`/api/tick`** is locked by `CRON_SECRET` (constant-time comparison; refuses to run if the secret is unset or short). Whoever holds the secret can only trigger "send due alerts", which is harmless.
- **Push** uses VAPID (ES256); the key pair is generated on first use and stored in Redis. There are no secrets in the repo; the only variable you set is `CRON_SECRET`.
- **Commits** use the GitHub no-reply address, so no personal email is in the history.
- **If the sync code leaks:** Unlink on every device, flush the `f21:*` keys in Upstash, delete the blobs in the Blob store, create a new code.
- Local data lives in the browser (localStorage + IndexedDB); anyone with access to an unlocked device or profile can read it.
- No rate limiting on the public endpoints beyond what Vercel provides.

## How it works

- **Schedule engine** (`data.js`): `buildDay(date, state)` returns that day's blocks from wake time, mode (Home / Hyderabad), office-vs-WFH, travel flag and weekday. Meals come from a small database (kcal, protein, fibre per serving) plus a PG menu planner.
- **Targets:** Mifflin-St Jeor BMR × 1.55 activity − 650 kcal; protein 2 g per kg of goal weight; fat 0.8 g/kg of goal; remaining calories as carbs; 35 g fibre; 3.5 L water. Estimates only.
- **Coach** (`app.js`): rule-based over the last 7 days (training, meals, content, sleep adherence; steps; weigh-ins; weight trend per week vs 0.25 to 1.2 % body weight) to produce warnings and praise.
- **Notifications:** while the app is alive it fires alerts itself. With push on, the page uploads its next ~2 days of alerts; an external timer calls `/api/tick` each minute; `tick` finds due alerts and sends an **empty** Web Push (so no payload encryption is needed); the service worker then asks `/api/next` what to show. Done/Skip taps are applied locally and sent to the server so other devices update and follow-ups are cancelled.
- **Sync:** every synced key carries a modified-time; map-like keys (done, steps, weights...) are unioned per entry and the newer key wins on conflict; deletions are remembered as tombstones. Undo stores `''`/`null` rather than deleting, so it syncs too.
- **Photos:** resized to 1280 px JPEG in the browser, stored in IndexedDB, encrypted before upload (4 MB limit per file), fetched and decrypted on demand on other devices.

## Build history

Everything done, in order.

### v1.0: the app (front end)
- Searched existing sessions for a routine/gym app: none existed, so it was built from scratch.
- Built `data.js` (schedule builder, meal DB, workouts, targets, alert generator), `store.js` (state + IndexedDB), `app.js` (five views, sheets, notification scheduler), `styles.css`, `index.html`, the PWA manifest and the service worker.
- Design choices: flat colour (dark ink with lime accent, no gradients), Outfit + Plus Jakarta Sans, SVG rings, line chart, sheets, staggered page transitions, confetti on a perfect day, splash with a drawing ring.
- Generated PNG icons with a PowerShell/System.Drawing script (no Node or Python available) and wrote a PowerShell static server for local testing.
- Camera/gallery capture uses `<input type=file capture>`; photos are resized and stored locally.
- Notification actions (Done / Skip / Add photo) are handled in the service worker and written to an IndexedDB queue that the page merges on open.

### v1.1: fixes found while testing
- Weekend schedules had overlapping blocks (explore vs breakfast/lunch; second long video vs snack). Split the explore block around lunch and re-timed the second long video. A checker now confirms no overlaps for every weekday × mode × office/travel × optional-video combination.
- Fuel listed pre/post-workout meals on days that have none (Sunday) and the planned totals counted them. Meals now follow the day's schedule.
- Meal notifications used a clock emoji; now a plate.
- The accent colour was too faint in the light theme; deepened for light mode only.
- Verified: planned intake (about 2,600 kcal, 160 g protein) lands close to the computed target.

### v2.0: sync and server push (first backend, Netlify Functions)
- Added `merge.js` (shared merge), `sync.js` (sync client, push subscription) and a backend with the routes now in `api/`.
- Design decisions that carried through every later version: **empty pushes** (service worker fetches the text) to avoid payload encryption; **VAPID with Web Crypto only** (no dependencies, testable in a browser); VAPID keys auto-generated and stored server-side (no env var); alerts computed on the client and uploaded, so the server has no copy of the schedule logic.
- Service worker: push handler, never caches `/api`, reports Done/Skip taps to the server.
- Settings: sync card (create code, link a device, push on/off, unlink); onboarding has a "link existing code" path.

### v2.1: security and privacy hardening
Found in an audit and fixed:
- Imported or synced data was not validated → strict whitelist sanitiser shared by browser and server; own-property copy so a `__proto__` key cannot alter prototypes; IDs must start alphanumeric.
- Anyone who found the URL could create storage → single-owner lock (HTTP 403 for any other sync id).
- Photos were stored unencrypted on the server → client-side AES-GCM encryption; server stores ciphertext only; decrypted MIME types whitelisted.
- No security headers → strict CSP, HSTS, nosniff, no-referrer, COOP/CORP, frame blocking, `noindex` (header, meta and robots.txt).
- Defaults leaked personal details on the public site → weight fields start blank at onboarding with neutral state defaults; the recurring venue commitment is now an editable name ("Venue shoot" by default).
- Backup import only accepts photo data for known ids and whitelisted data-URL types.
- Scanned the repo for secrets and personal data: none.

### v2.2: repository
- The assistant's browser blocked GitHub and Netlify (organisation policy) and there is no GitHub CLI, so repo creation and deployment were left to the owner; the policy was not worked around.
- First local commit used a GitHub no-reply identity (repo-local config only).
- The owner created the private repo (it held GitHub's initial README commit). A first push was rejected as non-fast-forward; the remote commit was merged in with the project README kept, and nothing was force-pushed. An automatic safety check then declined one push, so the project was moved to a real folder, the repo rebuilt there on top of GitHub's commit, and pushed.

### v3.0: moved from Netlify to Vercel
- Decision: the owner chose Vercel (already used for another project). Vercel is also blocked in the assistant's browser, so deploying stays with the owner.
- Rewrote the backend as Vercel Functions in `api/` (CommonJS, one file per route, shared code in `api/_lib/`). `public/merge.js` is imported by `api/sync.js`, so browser and server still share one merge and validation implementation.
- Storage: **Upstash Redis** for state, push records, the owner lock and VAPID keys (strongly consistent, atomic `SET NX` for the lock). **Vercel Blob** for encrypted photos (Redis' request-size limit and free quota are too small for photos). Blob alone was rejected for state because Vercel Blob is CDN-cached, which breaks read-modify-write merging.
- Scheduling: Vercel's free plan only runs cron once a day, so `/api/tick` is an HTTP endpoint protected by `CRON_SECRET` and called every minute by a free external timer.
- Photo size limit is 4 MB (Vercel's request-body limit is 4.5 MB). The service-worker cache version was bumped to v3.
- Removed the Netlify files (`netlify.toml`, `netlify/`) and updated headers to `vercel.json` (same CSP and headers).

## Decisions and assumptions

All editable in the app or in `public/data.js`.

- Wake 05:45, lights out 22:15 (about 7.5 h sleep; later bedtimes cut that).
- Weekday: gym 06:15 (1h45; 1h30 on office days), shift 11:00 to 20:00, stand-up 11:15, lunch 13:00, dinner 20:00, night walk 20:30 to 21:30.
- Office days default to Monday and Tuesday (toggle any day). Commute is about 2 km on foot or by bike.
- Daily reel: a 45 min creation block before work plus a flexible 45 min "post and reply" slot in a free gap.
- Friday 17:00 plans the long video; Saturday shoots, Sunday edits and uploads; an optional second weekly video is a setting.
- Steps: 10K on weekdays, 25K on a travel day, 12K on the other weekend day. Sunday is the travel day by default; Saturday is gym.
- PG menu defaults: eggs Tuesday and Friday, chicken Thursday and Sunday; other days are self-managed (eggs, soya, curd).
- Training split: chest twice a week (heavy Monday, volume Friday), back + biceps, legs, shoulders + core, a full-body Saturday and Sunday mobility. Belly fat is treated as a result of the deficit and steps; core work builds the muscle underneath.
- A recurring venue shoot: visit about every 12 days, post at least every 3 days (name and intervals editable).
- A large weight goal is shown as a months-long journey; the 21 days are the launch. A weekly loss of 0.25 to 1.2 % of body weight is treated as healthy.
- Calories and macros are estimates, not medical advice; check with a doctor before big diet changes.

## Known limits and next steps

- Not yet deployed; the live link is missing until the owner imports the repo on Vercel.
- Push is untested on real devices. It depends on an external one-minute timer, so alerts can be about a minute late and stop if the timer stops. iPhone needs iOS 16.4+ and the app added to the Home Screen.
- Numbers and notification text are readable by whoever owns the Upstash database (only photos and reports are end-to-end encrypted).
- Redis updates are read-modify-write without a lock; with a single owner on a few devices a lost update is possible only if two devices sync in the same instant, and the next sync repairs it.
- Photo and report files are limited to 4 MB each; larger ones stay on the device they were added on.
- Fonts load from Google Fonts. Self-hosting them would remove the last third-party request.
- No in-app AI analysis of photos or reports; they are stored privately, and analysis is done by sharing them in a chat with the assistant.
- Ideas: rate limiting, a workout log with sets and reps, an offline photo-upload queue.

## Maintaining it

```powershell
# run locally (front end only; sync shows "server not found" because /api runs on Vercel)
powershell -ExecutionPolicy Bypass -File dev/serve.ps1 -Port 5173

# regenerate the PNG icons
powershell -ExecutionPolicy Bypass -File dev/make-icons.ps1

# rebuild the static-only zip
Compress-Archive -Path public\* -DestinationPath forge21-netlify-deploy.zip -Force
```

- After changing any file in `public/`, bump `VER` in `public/sw.js` so installed apps refresh their cache.
- Keep the Content-Security-Policy in `vercel.json` identical to the one in `dev/serve.ps1`.
- `public/merge.js` is shared by the browser and `api/sync.js`; change it in one place and re-test both sides.
- Environment variables used: `CRON_SECRET` (you set it); Upstash and Blob variables are added by connecting the stores.
